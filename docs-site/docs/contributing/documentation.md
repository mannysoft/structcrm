# Writing documentation

The public documentation lives in `docs-site` and is built with
[Docusaurus](https://docusaurus.io). The `docs/` folder at the repository root holds
**internal** design material (PRD, architecture, database design, roadmap) and is not part
of the published site.

## Structure

```text
docs-site/
├── docusaurus.config.ts        # site metadata, navbar, footer, theme
├── sidebars.ts                 # section order (each section is autogenerated)
├── src/css/custom.css          # brand palette + landing page styles
├── src/pages/index.mdx         # landing page
├── static/img/                 # logo, favicon, social card
└── docs/
    ├── intro.md
    ├── getting-started/        # 6 pages
    ├── user-guide/             # 28 pages
    ├── developer-guide/        # 16 pages
    ├── api/                    # 6 pages
    ├── operations/             # 6 pages
    └── contributing/           # 4 pages
```

Page order inside a section comes from `sidebar_position` in front matter. Sidebar sections
themselves are declared in `sidebars.ts` and autogenerate their contents.

## Add a page

1. Create the file in the right folder, kebab-case: `docs/user-guide/submittals.md`.
2. Add front matter:

   ```markdown
   ---
   title: Submittals
   sidebar_position: 17
   description: One sentence that becomes the meta description and card summary.
   ---
   ```

3. Write the content starting with a single `#` heading.
4. If you inserted a page in the middle, bump the `sidebar_position` of following pages.
5. Build and check:

   ```bash
   cd docs-site
   npm install          # first time only
   npm run build        # broken links fail the build
   npm run serve        # preview at http://localhost:3000/structcrm/
   ```

## Writing style

| Do | Don't |
| :--- | :--- |
| Address the reader as "you" | "The user should…" |
| State the behaviour that exists today | Describe what the PRD hopes to build |
| Use tables for field lists and option matrices | Long prose lists of fields |
| Use `:::tip` / `:::warning` / `:::danger` for genuinely exceptional notes | Decorate every paragraph |
| Tag code fences (`bash`, `php`, `json`, `http`, `dotenv`, `text`) | Untagged fences |
| Link with absolute doc paths: `[Budgets](/docs/user-guide/budgets)` | Relative file links between docs |
| Show the command *and* what success looks like | Bare commands |

Rules of thumb:

- **Accuracy beats completeness.** If the code does not do it, do not document it — or
  document the gap explicitly.
- **Name the file.** When a behaviour lives in a specific class or config, mention it
  (`CreateBillingAction`, `config/filesystems.php`) so readers can verify.
- **Warn about consequences.** "Approving twice creates a second budget" belongs in a
  `:::caution`.
- **Keep examples runnable.** Copy-pasteable commands with realistic values.

## Links and anchors

- Docs use absolute paths: `/docs/developer-guide/testing`.
- Anchors are generated from headings; heading `## How amounts are calculated` becomes
  `#how-amounts-are-calculated`.
- `onBrokenLinks: 'throw'` means a bad link fails `npm run build` — that is the test.

## Images

Put images in `docs-site/static/img/`. Prefer SVG for diagrams and short screenshots. Every
image needs alt text. Do not add screenshots of demo data containing real client names.

## What not to include

- Credentials, API keys, `.env` values, tokens.
- Customer data or real project names in examples.
- Marketing copy — the docs explain the product, not sell it.
- Promises about unreleased features.

## Versioned docs

There is no versioned documentation yet: the site documents `main`. When the first stable
release is tagged, add a version with `npm run docusaurus docs:version 1.0` and document the
release process.

## Reviewing documentation

When you review a code change, ask:

1. Does it change behaviour, configuration or the API?
2. If yes, is the matching page updated?
3. Would a reader following the docs hit the behaviour you just changed?
